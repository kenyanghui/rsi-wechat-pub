你收藏夹里躺着 37 篇「一人公司 AI 团队搭建」。

上周末你终于动手了。照着某篇爆款里的岗位表，先搭内容 Agent，再搭客服 Agent，第三个准备做数据分析。三天后：内容 Agent 写出来的东西像通稿，客服 Agent 把客户一个个惹毛，销售 Agent 发出去的邮件没人回。你把 prompt 改了十几版，越改越乱。

然后你得出一个结论：模型不行，或者我不行。

都不是。你抄的是那张岗位表，没抄到让这 16 个岗位不打架的那套「接口」。**岗位表是组织架构的输出，不是输入。** 你把它当成了施工图，其实它是竣工照片。

上一篇我们拆的是一家 AI 一人公司「卖什么、怎么收钱」。这一篇往下沉一层：他凭什么一个人管得住 16 个岗位。

先把话说明白：文中涉及的第三方岗位设置与经营数据，均来自公开报道与作者自述，本文未独立验证，不为其真实性背书。

## 一、拆开看：16 个岗位，只有 6 个直接对着收入

素材里的原型不复杂：一位创始人拿自己的产品（一个 AI 工作流平台）运营自己的公司，16 个 Agent 分别负责内容创作、SEO、社媒、客服、销售、邮件营销、付费广告、竞品监控、用户反馈、产品更新、发票处理、日程、文档、技术支持、数据分析、品牌监控。

多数人看到这张表的第一反应是「我也要」。量化人看到这张表的第一反应应该是：先分类。

我按「与收入的因果距离」把它们重切了一遍（**这是本文的拆解框架，不是原文的分类**）：

- **直接承接收入**，获客与转化：内容、SEO、社媒、销售、邮件营销、付费广告，6 个；
- **交付与履约**，决定留存：客服、技术支持、文档、发票、日程，5 个；
- **情报与后台**，决定迭代速度：竞品监控、用户反馈、产品更新、数据分析、品牌监控，5 个。

![](imgs/fig1_layers.png)

*图 1：按「与收入的因果距离」重切 16 个岗位（本文框架，非原文分类）*

切完，反常识自己就浮出来了：**16 个岗位里，只有 6 个直接承接收入。** 另外 10 个不产生收入，但它们决定这 6 个能不能留下来——客服决定客户续不续费，文档决定客户能不能自助，数据分析决定你下一笔预算放在哪。

说它们「在维持系统不失血」不算错，但更准的说法是：**它们不产生收入，它们决定收入能不能留存。**

而新手最爱先搭的，恰恰是内容 Agent 和数据分析 Agent。

内容 Agent 的问题不是写不好，是「好不好」没有可验收的口径。这里要拆细，一篇内容的验收其实分两层：

- **合规层**：事实有没有错、链接能不能点、数据有没有来源。这层今天就能写完，写完就能判定，几分钟一个；
- **效果层**：打开率、读完率、带来了几个咨询。这层能测，但短期不可归因——一个人一周发三篇，样本量根本不足以区分「选题不对」和「运气不好」。

崩的地方就在这里：直接拿效果层当验收标准，而效果层三个月也定不下来，于是只能退回到「读起来还行」。**「还行」不是一个能签字的标准**，所以你只能一直改 prompt，改到怀疑自己。

数据分析 Agent 的问题更硬：你根本没有数据。一个人公司，一天两百个访客，跑不出任何统计显著性。它最后能给你的，是几张漂亮的图和一段听起来很有道理的归因。这类产出比没有产出更危险——它会让你做出一个自信的错误决策。

再说句公道话：不是后台岗位不重要，是**因果距离决定验收方式**。离收入近的，验收看转化；离收入远的，验收看它有没有缩短你的决策延迟。用同一把尺子去量 16 个岗位，是你崩掉的第一个原因。

即便在那 6 个岗位里，顺序也不能乱。先做离成交最近的那个：如果你现在只有咨询收入，就先搭能直接接住咨询线索的那个，而不是先做品牌监控。**先修水管，再装净水器。**

## 二、一人公司不是「人少」，是「接口多」

原文里有一句话很克制，也是全文最值钱的一句：**AI Agent 是放大器，不是创造器。**

前提是你得先知道卖什么、卖给谁、解决什么问题。放大器有个残酷属性：它同时放大你的产能和你的混乱。流程不清的团队上 AI，得到的不是效率，是更快的返工。

那么「接口」到底是什么？我把它拆成四类，你可以直接拿去对照手上已有的 Agent。

![](imgs/fig2_interfaces.png)

*图 2：四类接口，一页纸的检查清单*

**一、权限接口：它能碰什么，不能碰什么。**

三个必须回答的问题：能不能直接对外发消息？能不能动钱？能不能改生产环境？默认答案都应该是「不能」。让一个 Agent 拥有对外发言权而不设审核，等于把公司信用挂在一个概率模型上。

**二、接管接口：什么条件下必须人工介入。**

原文提到「人工接管触发条件」。翻成风控语言，这就是**强制平仓线**——不是等它做错了再补救，而是提前写好「出现这几种情况，立刻停手，转人工」。比如涉及退款、涉及承诺交付时间、涉及任何对外报价。没有触发条件的 Agent，不叫自动化，叫失控。

**三、验收接口：什么样的产出算通过。**

注意是「可证伪」，不是「感觉还行」。而且验收要分两层，顺序不能反。

**合规层**，今天就能写完，判定成本几分钟。一篇内容算通过，可以是「事实错误为零、链接全部可点、至少一个可验证的数据来源」；一条客服回复算通过，可以是「24 小时内响应、未作出任何超出服务条款的承诺」。

**效果层**，能测，但短期不可证伪。阅读、转化、留存，至少要三个月、且样本量够，才有解释力。它的用途不是「判断这个 Agent 行不行」，而是「判断这条路还要不要继续加钱」。

所以「写不出验收标准，说明这个岗位对应的业务你自己还没想清楚」这句话，要限定在合规层：**连合规层都写不出来的岗位，你根本不知道它交付什么。** 效果层写不出来是常态，那不是你不行，是样本不够。

**四、记忆接口：它凭什么知道你的偏好。**

原文给的两个数字很实在：10 到 20 篇风格样本、50 到 100 条 FAQ。本质是**给 Agent 装先验**。没有先验的 Agent，每次都从零开始猜你，猜错的成本由你承担。

四个接口，缺一个，Agent 就会在某个你没预设的地方给你制造惊喜。

这里有一道容易被忽略的算术题：**每加一个 Agent，增加的不是一份工作量，是一组接口。** 16 个 Agent 两两之间，理论上有 120 条边（C(16,2)=120）。你搭到第 3 个就崩，不是模型不行，是边数在平方级上升，而你的接口一条都没建。

所以那句话应该改写：**一人公司的护城河不是「我有 16 个 Agent」，而是「我知道第 7 个 Agent 出错时，谁会拦住它」。**

我自己复盘过三个搭崩的案例，崩点全在权限，没有一个在模型能力。其中一个最典型：销售 Agent 擅自给客户报了一个折扣，金额不大，但那是合同风险，不是效率问题。

顺带做个工程对照：我翻过的几个开源多 Agent 编排方案（包括围绕 OpenClaw 这类工具搭团队的公开实践），都把「角色定义 + 权限边界」写在流程编排之前。样本不大，算不上统计结论，但这几个案例的翻车点高度一致——不是模型不会做，是没人规定它什么时候必须停下来问一句。

四类接口写下来，其实就是一页纸。但这一页纸，决定了你后面 15 个 Agent 是资产还是负债。

## 三、复刻：把组织当策略，做一次回测

到这里，复刻才有意义。但复刻的对象不是那张表，是节奏。

**第一步，单因子验证，第 1 个月。**

只上 1 个 Agent。选「最痛且最可验收」的那一个——痛点决定你有没有动力维护它，可验收决定你能不能判断它是否有效。

举个具体的：如果你 60% 的时间花在回客户重复问题上，那就先做客服 Agent，别做内容。因为客服的输入输出边界清楚，验收标准可以写成「响应时长 + 承诺越界次数」；而内容的效果层验收，你三个月也定不下来。

通过标准要写死在前面：**每周省下的时间 ≥ 搭建与纠错成本，连续 3 周成立。** 更硬的一条：同一批任务，Agent 版返工次数不高于手做版。

退出条件同样写死：3 周不达标，砍掉，换下一个。不许「再调调 prompt」——这句话是沉没成本给大脑下的药，我吃过。

单因子不过，不要加第二个。加了也不会好，只会让你同时失去两个变量的解释力。

**第二步，分批建仓，第 2 到 6 个月。**

原文建议每月增加 1 到 2 个。这在量化语言里就是**定投式扩容**：不预测拐点，只控制单次暴露。

一次性上 16 个，等于满仓单票。你以为自己在分散，其实所有 Agent 共享同一个你——同一个判断力瓶颈、同一套没写下来的规则。它们会同时犯同一类错，相关性接近 1。这不是分散，是加杠杆。

还有一条硬规则：**每加一个 Agent，必须同时加一条接管规则，否则不许上线。** 先写刹车，再装发动机。

**第三步，单位经济核算，每季度。**

算三个数：单岗位节省工时、返工率、以及那个灵魂拷问——**「没有它，会不会更慢？」**

第三个数字最伤人。很多 Agent 的真实作用是让你觉得在做事情，而不是让事情变少。它们的产出需要你花更多时间去读、去改、去圆场。

这三个数要用可证伪的口径算：工时记录、返工记录、任务完成时间，而不是回忆。回忆会自动美化你投入的那部分。

我还会加第四个：维护成本。Prompt 会折旧，模型会升级，接口会变。一个三个月没人管的 Agent，不是资产，是负债。

**然后是不可复刻项。**

创始人的产品判断力；他手上已经有真实业务，可以拿自己的公司当试验田；以及「16」这个数字本身的传播红利。

**数字是叙事，不是方法。** 你抄到 16，只抄到了一个营销素材。

## 四、风控：真正的尾部风险不在技术

这一段，市面上的「AI 团队搭建」文基本不写，但它是量化线必须写的。

一人公司在法律上常与个人财产高度耦合。主体混同、合同主体不清、数据与隐私合规、AI 生成内容的版权与责任归属——这四件事的共同点是：**平时不出现，出现就归零。**

用风险语言说，这不是波动率，是**尾部风险**。波动率会让你难受，尾部风险会让你出局，而本金不可再生。

具体到 Agent 身上，风险会被放大，因为它的行动速度比你快。

- 一个客服 Agent 随口承诺了服务条款里没有的赔付，那是合同风险；
- 一个销售 Agent 群发了未脱敏的客户名单，那是数据合规风险；
- 一个内容 Agent 引用了不存在的研究，那是版权与声誉风险，而且会被截图。

所以边界要像设止损一样设在事前：主体隔离，别用个人账户收公司的钱；合同留痕，谁签的、什么时候、什么版本；数据分级，哪些数据永远不进 Agent 的上下文；对外内容人工终审，尤其是涉及价格、承诺、法律表述的部分。

还有一个细节常被忽略：发票与收款。让 Agent 处理发票没问题，但收款账户、开票主体、合同签署人必须是同一个法律主体。三者不一致，前面所有自动化省下的时间，都会在第一次纠纷里连本带利还回去。

**16 个 Agent 里，最不能自动化的是「签字」。** 不是因为机器不会签，是因为签字意味着有人要承担后果。你可以把 90% 的流程交出去，但那 10% 的责任，交不出去。

## 五、结尾：把「财富自由」还原成一条曲线

我不打算在这里许诺什么。任何告诉你「搭完 16 个 Agent 就自由了」的人，卖的是课，不是方法。

能说的只有一个结构：

**一个人的产能上限 ≈ 他能固化的 SOP 数量 × 每条 SOP 的调用频次。**

这两个乘数都能估，不用凭感觉。

**一条 SOP 是什么？** 你每周至少做一次、并且能写成 step 1/2/3 的事。写不成步骤的，是手艺，不是 SOP。所以「数量」这一项，直接数你上周重复做过三遍以上的事就行。

**调用频次是什么？** 这件事一个月发生几次。客服问答 40 次/周，就是 160 次/月；月度报表 1 次/月，就是 1 次。

两个数一乘，顺序就出来了：**频次最高的那件，哪怕每次只省 5 分钟，一个月也是 13 个小时；频次最低的那件，哪怕省 2 小时，一个月也只省 2 小时。** 新手总在优化后者，因为后者看起来更「高级」。

注意，这两个乘数都不是「Agent 数量」。Agent 只是执行器。真正沉淀下来的是五样东西：工作流是骨架，Prompt 是说明书，权限是边界，知识库是记忆，持续优化是迭代。

这五件事标准化之前，你搭的不是公司，是一份更累的零工——只不过工位从办公室搬到了浏览器。

所以今晚可以只做一件事：打开你收藏夹里那篇「16 个 AI 员工」，别看岗位名，只看每个岗位的验收标准。

**连合规层验收都写不出来的那个，就是你现在不该先搭的那个。**

这句话的意思不是那个岗位不重要。是那个岗位对应的业务，你自己还没想清楚。而 Agent 不会替你想清楚——它只会把你没想清楚的部分，放大 16 倍。
